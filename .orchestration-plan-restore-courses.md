## Task Classification

**Feature** (Admin Ops)

---

## Summary

Add an admin-only dashboard view to display soft-deleted courses with the ability to restore them (set `deleted_at = null`). This feature touches admin operations, database modification (restore), and authorization.

---

## Complexity

**Medium** — Multiple files and API routes needed (UI, API endpoint, authorization checks), but constrained scope to admin dashboard without schema changes or cascading effects.

---

## Risk Assessment (Using Updated Rubric)

### Auth Risk

**Medium** — This adds a new admin action that restricts visibility of soft-deleted courses to admin role only; must ensure non-admin users cannot access the restore endpoint or view deleted courses. Reuses `requireApprovedApiUser()` guard but introduces new admin-specific resource visibility.

**Rubric basis:** Admin ops risk criteria (Medium) — "Admin action that changes records" (restore)

### DB/RLS/Storage Risk

**Medium** — Restore operation modifies `courses.deleted_at` from non-null to null, changing course visibility. Does NOT cascade to `student_course_tutors.is_active`. Query filters for soft-deleted courses differ from normal queries.

**Rubric basis:** DB/RLS/Storage risk criteria (Medium) — "Soft delete or restore behavior" and "Query filter changes involving `deleted_at` or `is_active`"

**Risk escalation triggered:** "Any restore or soft-delete reversal is at least Medium"

### Admin Ops Risk

**Medium** — Adds a new admin action that modifies persistent records (restore); must include proper confirmation to prevent accidental restores. Does not include cascading assignment reactivation.

**Rubric basis:** Admin ops risk criteria (Medium) — "Admin action that changes records" and "Restore"

### AI/Chat Risk

**None** — No AI/chat behavior touched; restored courses will resume normal chat behavior only when active assignments are re-established separately (unchanged).

### File Access Risk

**None** — No file behavior touched; restore does not affect file storage or access.

### Release Risk

**Low** — Feature is isolated to admin UI and API with no env var, deployment, or auth settings changes required.

## Architect Decision (Pre-Implementation)

**See `docs/architecture/decisions/0001-restore-soft-deleted-courses.md` for full details.**

✅ **Restore sets ONLY `courses.deleted_at = null`**

❌ **Does NOT automatically reactivate `student_course_tutors.is_active`**

Rationale: Course visibility and assignment status must remain decoupled so restoring a course doesn't bypass the intent to pause student access. If assignment reactivation is needed, it must be a separate explicit admin action.

## Mandatory Studdy Buddy Rules to Verify

1. Do not bypass existing auth helpers; use `requireApprovedApiUser()` in the restore endpoint.
2. Do not trust `courseId` directly from the request; validate admin role first.
3. Return `404` (not `403`) for unauthorized access to prevent leaking course existence.
4. Do not hard-delete courses; always preserve soft-delete pattern.
5. Preserve `courses.deleted_at` soft delete — restore sets it to null, never removes the column or data.
6. Do not automatically modify `student_course_tutors.is_active` during restore; if needed, make it a separate action.
